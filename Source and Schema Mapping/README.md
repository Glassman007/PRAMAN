# PRAMAN Source & Schema Mapping — Prompt 5

This module contains the feature-complete Source & Schema Mapping workspace from Prompts 1–4 plus the Prompt 5 data-integrity, hardcoding, semantic, performance, visual-cleanup and regression audit. No new major dashboard feature is introduced in Prompt 5. See `FINAL_AUDIT.md` for the verified report and limitations.

## Scope boundary

The module remains strictly pre-matching:

`RAW SOURCE → INGESTION / ADAPTER → VALIDATION → SCHEMA DETECTION → FIELD MAPPING → TRANSFORMATION → NORMALIZED SOURCE STATE`

It does not perform or imply parcel matching, conflict resolution, reconciliation, or authoritative-state selection. `SOURCE_OBSERVATIONS`, conflicts, reconciled parcels, canonical parcel values, and GeoGit parcel history are not used to manufacture Source & Schema Mapping state.

## Quality & Exceptions

The contract generator now calculates source and field quality directly from the current dataset:

- populated and null/empty values;
- completeness ratio (reported as a measurable dimension, never as an overall quality score);
- unique values and repeated-value occurrences;
- datatype/range validation only where `DATA_DICTIONARY` defines a testable rule;
- source-specific schema conformance against `SOURCE_SPECIFIC_SCHEMA`;
- duplicate identifiers;
- geometry-reference integrity;
- recorded geometry transformation consistency.

The exception queue contains only detected violations. Issue categories are generated by the actual validation logic and filter options are generated from categories present for the selected source.

For the supplied dataset, strict pre-match exceptions are present only where required non-historical-nullable source-specific values are actually empty. Clean sources receive an empty exception state rather than demo rows.

## Original vs normalized records

The supplied dataset does **not** contain upstream raw source-record tables. `MATCHING_INPUT_VIEW` is already the normalized pre-match state.

Therefore the record inspector never labels it as raw input. It shows:

- an explicit **Original source record unavailable** state;
- preserved source-native attributes that actually exist inside `source_specific_details`;
- the real normalized `MATCHING_INPUT_VIEW` row for the detected exception;
- the real associated `SOURCE_GEOMETRIES` row when available.

This prevents a normalized record from being misrepresented as an original record or as a canonical parcel.

## Lineage & Impact

The provenance view renders only reconstructable stages.

For explicit geometry normalization, PRAMAN can show:

`Source → geometry record → original field/value → normalization_method → normalized field/value`

because all of those values are stored together in `SOURCE_GEOMETRIES`.

For retained source-native attributes and normalized non-geometry fields, upstream raw field/rule provenance is incomplete. The UI stops at the strongest available evidence and displays the limitation rather than filling in missing stages.

Mapping impact is calculated from the current mapping relationships and configuration. It can show affected-record counts, normalized attributes, recorded transformations, and validation/configuration dependencies. It does not claim impact on matching, conflicts, reconciliation, or authoritative state.

## History & Configuration

No pre-match source import/schema/mapping version history, reviewer events, approval/rejection events, or reusable mapping templates are present in the supplied data. The History view therefore displays the required empty states.

The current mapping configuration remains inspectable and exportable. Export includes only:

- the relationships actually visible in the workspace;
- recorded geometry transformation methods;
- normalized identifier representations;
- the actual source-specific validation configuration;
- the normalized data-dictionary datatype definitions.

It does not create source→canonical mappings or hidden UI-only fields.

## Cross-view workflow

The workspace preserves the selected source and carries available field/mapping/exception context through:

`Schema Mapping → Quality & Exceptions → Lineage & Impact → History & Configuration`

Changing the selected source clears stale field/mapping context and rebuilds each view from that source's contract data.

## Main files

- `data-contract.json` — generated dataset-backed contract including exception rows and real normalized snapshots for detected exceptions.
- `scripts/build_data_contract.py` — reproducible read-only contract generator.
- `src/sourceSchemaMappingService.js` — selectors for mapping, quality, exceptions, provenance, impact, history and export configuration.
- `src/dashboard/SourceSchemaMappingWorkspace.jsx` — the five-view workspace.
- `src/dashboard/sourceSchemaMapping.css` — scoped PRAMAN styles.
- `test/qualityLineageHistory.test.mjs` — quality/lineage/history integrity tests.
- `test/full_integrity_audit.py` — source-by-source and hardcoding audit.
- `test/dataset_replacement_test.py` — controlled dataset replacement audit.
- `test/historyMetadataVariation.test.mjs` — history metadata/source-isolation regression test.
- `test/finalUiAuditRegression.test.mjs` — regression coverage for the final UI/function audit defects.
- `FINAL_AUDIT.md` — Prompt 5 implementation report and genuine verification boundaries.

## Regenerate the contract

```bash
python PRAMAN_SOURCE_SCHEMA_MAPPING/scripts/build_data_contract.py \
  PRAMAN_DATA \
  PRAMAN_SOURCE_SCHEMA_MAPPING/data-contract.json
```

## Validation

```bash
cd PRAMAN_SOURCE_SCHEMA_MAPPING
npm test
```

`npm run test:module` runs the self-contained selector/UI-regression suite. `npm run test:dataset` additionally verifies contract reproducibility and dataset replacement against the real sibling `../PRAMAN_DATA` directory. The dataset command intentionally fails instead of silently skipping when that directory is absent.
